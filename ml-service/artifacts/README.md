# `artifacts/` Directory

## Purpose
This directory stores all outputs generated by ML experiments, including trained models, evaluation metrics, visualizations, and experiment metadata.

## What Belongs Here
- **Trained models**: Serialized model files (.h5, .tflite, .onnx, .pkl)
- **Model checkpoints**: Intermediate training snapshots
- **Evaluation metrics**: JSON/CSV files with performance metrics
- **Plots and visualizations**: Training curves, confusion matrices, ROC curves
- **Experiment logs**: TensorBoard logs, training history
- **Model metadata**: Model cards, configuration snapshots

## What Should NOT Be Here
- ❌ Source code (belongs in `src/`)
- ❌ Configuration templates (belongs in `config/`)
- ❌ Raw or processed data (belongs in `data/`)
- ❌ Production-deployed models (should be in a model registry)

## Architectural Responsibilities
- **Experiment tracking**: Organize outputs by experiment ID or timestamp
- **Model registry**: Maintain history of all trained model versions
- **Reproducibility**: Link artifacts to specific code commits and configs
- **Comparison**: Enable easy comparison between different experiments

## Subdirectories

### `models/`
- Serialized model weights and architectures
- Checkpoint files from training
- Exported models for deployment (.tflite, .onnx)

### `metrics/`
- JSON/CSV files with evaluation results
- Performance metrics (accuracy, AUC, F1-score)
- Benchmark results on test datasets

### `plots/`
- Training/validation loss curves
- Confusion matrices
- ROC/AUC curves
- Feature importance visualizations

## Interactions with Other Directories
- **`src/models/`**: Training scripts save models here
- **`src/evaluation/`**: Evaluation scripts write metrics here
- **`notebooks/`**: Load artifacts for analysis and visualization
- **`config/`**: Model artifacts reference which config was used
- **`main.py`**: May load best model for inference or deployment

## Best Practices
1. **Organize by experiment**: Use structured naming like `YYYYMMDD_HHMM_experiment_name/`
2. **Tag with metadata**: Include git commit hash, timestamp, config snapshot
3. **Semantic versioning**: Version models (e.g., `v1.0.0`, `v1.1.0`) for production releases
4. **Storage management**: Archive or delete old experiments to save space
5. **Model cards**: Document model performance, limitations, intended use
6. **Exclude from git**: Add to `.gitignore`, use cloud storage or artifact registries
7. **Reproducibility**: Save enough metadata to recreate any artifact
8. **Compression**: Use compressed formats for large models

